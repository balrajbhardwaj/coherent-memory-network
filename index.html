Executive summary

Business teams can now describe what they need in plain English and have a working application in hours. The speed is real, and so is the risk. When a person or an AI agent cannot easily find the approved source for a piece of data, they use the nearest one, and an ungoverned data path is born. Repeat that across many teams and many agents and the result is fragmentation at scale.

This paper argues that AI does not lack data. It lacks context. It needs to know where data should come from, whether it is fit for the task, whether the rules are enforced at the moment of use, and whether the consumer is entitled to it. Most organisations hold this context in documents, spreadsheets and people's heads. AI agents can read none of them.

The Coherent Memory Network is a design discipline for turning that context into something machines can query. It is built from five components:

  • Authorised Source Registry: where should this data come from, and who owns it?
  • Fitness for Purpose Framework: is this data suitable for this specific task?
  • Runtime Controls: are the data quality rules enforced at the point of consumption?
  • Governed Access: is this consumer entitled to this data, for this purpose?
  • Organisational Reality Map: how does the business actually work, and who acts when something breaks?

Each component answers its question at runtime through a shared service. Together they form one capability, run by five roles and adopted in four stages of maturity. The network is not a product. It is built component by component, domain by domain, on top of the catalogues, controls and governance forums that most regulated firms already have.

Chapter 1

Your AI is only as good as its memory

First published on LinkedIn, 8 April 2026

Business users can now describe what they need in plain English and watch a working application appear in hours. This is sometimes called vibe coding. There is no backlog and no six month wait for IT.

The intent is good and the speed is impressive. But it quietly introduces risk, and the risk is not in the code. It is in the data.

When the source is not the source

Consider a regulatory reporting analyst who needs Legal Entity Identifier (LEI) data to enrich transaction reports. The organisation already has an approved source: a vetted entity data provider, integrated into the firm's data supply chain with proper controls.

But the approved source is slow to update, hard to access, or stuck behind a long backlog. So the analyst builds a quick tool that pulls LEI data straight from the GLEIF API. They add some string matching on entity names, a few formatting tweaks and some manual overrides. It works. It fills the gaps.

The catch is that this logic is an uncontrolled end user computation. It has not been tested or reconciled against the approved source. It sits outside change management. And a downstream report, possibly submitted to a regulator, now relies on data from an ungoverned pipeline built in an afternoon.

It is a rational response to a bottleneck. The result, though, is a shadow data path where accuracy and auditability become unknown at exactly the point where they matter most. Multiply this across dozens of teams, each solving their own gaps with their own tools, and you get fragmentation at scale. Not because anyone did anything wrong, but because the foundation was not there to guide them.

Governance is the trust layer

If organisations want AI outputs they can rely on, the data underneath must be governed: approved sources, consistent definitions, quality controls and traceable lineage.

When applications took months to build, governance could catch up. When they are built in hours, governance must already be in place. It has to be part of the infrastructure, not added afterwards. In regulatory reporting or transaction monitoring the point is obvious. A model fed ungoverned data does not produce trusted outputs, and trust lost with a regulator is very expensive to rebuild.

Context must work for machines, not just people

Think of a business glossary as a dictionary. It tells you what a word means. It does not tell you which sentence to use it in, or when it would be the wrong word entirely.

AI needs more than definitions. It needs sourcing rules, fitness criteria and usage conditions, encoded in a form it can read and act on rather than buried in documents only a subject matter expert can navigate. Most organisations have built context for people. Very few have built context that machines can follow.

This is not a new idea. The semantic layer, enterprise knowledge graphs and data fabric architectures all point the same way: a machine readable layer of business meaning between raw data and the applications that consume it. Gartner suggests that organisations that prioritise semantics in AI ready data could improve generative AI model accuracy by up to 80% and reduce costs by up to 60% by 2027 [1]. Microsoft's launch of Fabric IQ, a semantic ontology layer designed to ground AI agents in business context rather than raw database schemas, reinforces the shift [2]. The direction of travel is clear. The challenge is turning it into something practical and grounded in how an organisation actually works.

A blueprint: the Coherent Memory Network

What organisations need is not another platform or product. It is a design discipline that acts as institutional memory for AI. I call it the Coherent Memory Network. It draws on the principles behind semantic layers and knowledge graphs, but frames them as an interconnected, governed system rooted in organisational reality.

Together, these components form a coherent memory that AI can navigate. It is not a single database. It is a connected framework that reflects the way the organisation actually operates. The rest of this paper takes each component in turn and shows how to build it.

Chapter 2

Start with an authorised source registry

First published on LinkedIn, 9 May 2026

The first component tells AI where to get data. The core argument of this chapter is simple: data modelling is how you capture context in a form that machines can read and act on.

The problem is not access. It is the absence of context.

Go back to the analyst from chapter 1. They did not lack access to LEI data. They lacked visibility. There was no clear, structured answer to a basic question: where should I get this data?

That question sounds simple. It is not. Behind it sit several layers of context: which system is the golden source, who owns it, what quality standards apply, which use cases it is approved for, and how it connects to other data in the supply chain. Today that context lives in people's heads, in emails, and in spreadsheets held together with good intentions. It is not modelled, not structured, and not available to an AI agent when it needs it.

What an authorised source registry is

An authorised source registry is a governed, modelled layer that maps key data elements to their approved sources, along with the context needed to use them correctly. It does not store data. It captures context about data: where it comes from, who is accountable, what standards it must meet, and when it may be used.

Think of it as a signposting system. It does not hold the goods. It tells you, and your AI, exactly where to find the right ones.

Why data modelling is the foundation

Without a model, a source registry is just a spreadsheet: static, flat and invisible to machines. With a model, it becomes a structured, queryable map of the data landscape that both people and AI agents can navigate. The context does not live in the individual data elements. It lives in the relationships between them.

The conceptual model

At its core, the registry has six entities:

  • Data Element: the basic unit of business data, such as Legal Entity Identifier, Counterparty Name or Trade Reference.
  • Source System: the system that holds or produces the data, such as an entity data provider, a trading platform or a reference data hub.
  • Domain: the business area accountable for the data, such as Reference Data, Trade Capture or Financial Crime.
  • Data Owner: the named person or role accountable within the domain.
  • Quality Standard: the measurable criteria the data must meet, such as completeness, timeliness and accuracy thresholds.
  • Use Case: the approved business purpose, such as regulatory reporting, transaction monitoring or management information.

The relationships are where the context lives:

  • A Data Element is sourced from one golden Source System but may exist as copies in several others. The model must say which is authoritative and which is derived. This is where most organisations fall short.
  • A Source System is owned by a Domain, and a Data Owner within that domain is accountable for the quality and availability of the data.
  • A Data Element has one or more Quality Standards, and those standards vary by Use Case. The same LEI data may need real time accuracy for transaction monitoring but can tolerate a one day delay for management reporting.
  • A Use Case is approved to consume from specific Source Systems only. Not all copies are equal, and the model must record which source is fit for which purpose.

This is not a flat list. It is a network of relationships that captures sourcing, ownership, quality and usage in one connected structure.

Not all data behaves the same

Reference data, such as LEIs and currency codes, is relatively stable, updates rarely and is reused widely. Master data, such as counterparty records and instrument details, changes more often and may have several contributing sources that need reconciling. Transactional data, such as trade events and payment instructions, is high volume, time sensitive and critical for lineage. Each type has different sourcing patterns, update frequencies and quality needs, and the model must reflect this. A single flat structure that treats an LEI the same as a trade event will not hold up in practice.

How to build it

A source registry does not need to be a massive programme. It is an iterative process led by domains, in four stages.

  1. Identify and prioritise. Start with the data elements that carry the highest sourcing risk. In financial services these are usually regulatory and compliance critical: LEI, counterparty identifiers, trade references, sanctions data. Ask one question: which data elements, if sourced from the wrong place, would cause the most damage? Fifty elements modelled well beats five thousand catalogued badly.
  2. Map sources and ownership. For each element, find the golden source, where copies exist, who owns the golden source and which domain it sits in. Work with domain teams directly. They know the real sourcing landscape, not the version drawn on architecture slides. This is where data mesh principles apply: the domain that produces the data owns its entry in the registry.
  3. Define quality standards and usage rules. For each element, spell out what good looks like for each use case: completeness thresholds, timeliness and accuracy. Most importantly, record which source is approved for which purpose. This is the step most organisations skip, and the one that would have prevented the GLEIF scenario in chapter 1.
  4. Model, publish and iterate. Build the conceptual model and validate it with domain owners and consumers. Then publish it in a form machines can query: an API, a knowledge graph or a semantic layer, not a PDF or a wiki page. Treat it as a living model and an operating capability, not a one off deliverable.

What a machine readable lookup looks like

If the registry is modelled properly, an AI agent building a regulatory report can query it and get a clear, structured answer.

# Query: Where should I source LEI data for regulatory reporting?
approved_source:   Entity Data Provider (System X)
domain_owner:      Reference Data, named owner
quality_standard:  99.5% complete, updated daily, reconciled against GLEIF weekly
usage_approval:
  regulatory_reporting:   approved
  marketing_segmentation: not approved
copies_exist_in:   System Y (trade capture), System Z (risk)
copies_status:     downstream consumers, not authoritative

This is the difference between a registry and a catalogue. A catalogue lists what exists. A registry tells you what to trust, and why.

Where most organisations stand

Most firms sit between two states. At one end there is no registry at all, and sourcing decisions are left to whoever builds the app. At the other is a static catalogue or data dictionary that documents sources but is not modelled, not maintained and not queryable by machines. Very few have a modelled, governed, machine readable registry that AI agents can use at runtime. That is the gap, and closing it is what makes the rest of the network possible.

Chapter 3

Fitness for purpose: why good data is not good enough

First published on LinkedIn, 17 October 2026

The registry tells AI where to find the right data. The next question is sharper: just because the data exists, is it right for the task?

An AI is only as good as the data it consumes, and the discipline with which it is allowed to consume it. When data is technically accurate but unfit for the job, AI does what AI does. It hallucinates, overreaches and confidently extrapolates beyond what the data can support. Bias creeps in and outputs drift away from the original ask. Most teams treat this as a model problem. It is also a data problem. The Fitness for Purpose Framework keeps AI anchored to what the data genuinely supports.

Good data is not universal

Most data quality programmes treat good as a single standard: data passes or fails one test. Take LEI data. The dashboard says it is 99% complete, accurate and reconciled daily. Green status. Good data. But good for what?

For management reporting it is excellent. For real time transaction monitoring, daily reconciliation is not enough. By the time an alert fires, the data may already be hours stale. Same data, same quality scores, two opposite verdicts. A single standard cannot hold both truths, yet most organisations still rely on one.

What fitness for purpose means

Fitness is not a single number. It is a view across several dimensions:

  • Timeliness: real time, intraday, T+1 or monthly.
  • Completeness: mandatory fields and coverage thresholds.
  • Accuracy: tolerance levels and reconciliation frequency.
  • Granularity: transaction level, aggregated or summary.
  • Lineage and audit: regulatory traceability requirements.
  • Approval status: which use cases the source is signed off for.

Different use cases weight these dimensions differently. The framework makes those differences explicit and measurable.

The framework

The framework has four parts:

  1. Quality dimensions: the standard set of measurable criteria.
  2. Use case profiles: for each approved use case, the required value on each dimension.
  3. Source to profile mapping: which sources meet which profiles, with evidence.
  4. Runtime validation: fitness checked at the point of consumption, not on a quarterly dashboard.

This is the layer that connects the registry to the decisions AI agents and applications make every day.

Why this matters for AI in particular

Human consumers make fitness judgements implicitly, through experience, business knowledge and common sense. AI agents have none of that. They take what they are given.

Without an explicit fitness framework, an agent will happily consume data that scores 99% on a quality dashboard but is completely unsuitable for the task, then produce confident, wrong outputs that look credible until someone with domain expertise spots the drift. This is also where hallucination compounds. Given data that is only partly fit, a model fills the gaps with patterns from training rather than grounded facts. It is doing what it was designed to do. The fitness framework stops it being asked to do it in the first place.

Data quality is a property of the data. Fitness for purpose is a relationship between the data, the task and the consumer. The first is necessary. The second is what keeps AI honest.

How to build it

  1. Define the dimensions. Standardise the language. Pick six to eight measurable criteria that actually matter, and avoid endless taxonomies.
  2. Profile the use cases. For each approved use case, set the required value on each dimension. Start with the highest stakes: regulatory, financial crime and risk.
  3. Map sources to profiles. For each source in the registry, evidence which use cases it can serve. Be honest. A source that meets four of six dimensions is partly fit, not fit.
  4. Make it queryable at runtime. Not a PDF or a wiki page, but a service that agents and applications call before consuming data.

What a fitness profile looks like

Here is a profile for transaction monitoring consuming LEI data. It is plain YAML, so it can be version controlled and read by machines.

use_case:
  name: transaction_monitoring
  domain: financial_crime
  approval_status: approved

fitness_requirements:
  timeliness:
    requirement: real_time
    max_latency_seconds: 5
  completeness:
    mandatory_fields: [lei, legal_name, jurisdiction, status]
    minimum_coverage_percent: 99.9
  accuracy:
    tolerance: zero_tolerance
    reconciliation_frequency: continuous
  granularity:
    level: entity_level
    aggregation_allowed: false
  lineage:
    audit_required: true
    source_evidence: required
  approval:
    approved_sources:
      - system_x_realtime_feed
    rejected_sources:
      - system_x_daily_extract
      - gleif_direct_pull

validation:
  pre_consumption_check: required
  failure_action: reject_and_escalate

The format is not the point. JSON or another structured language would work as well. What matters is that the profile is explicit, versioned and queryable. Together with the registry, it forms the contract an agent must meet before consuming data.

How the runtime check works

  1. An agent or application makes a request, for example: I need LEI data for transaction monitoring.
  2. The fitness service receives the request with the use case context.
  3. It evaluates the candidate source against the use case profile, dimension by dimension.
  4. It returns a structured verdict: fit, partly fit or not fit, naming any failing dimensions.
  5. The application proceeds, switches to an alternative source, or escalates.

This is the difference between data quality being monitored and fitness being enforced.

Chapter 4

Every agent is a control point

First published on LinkedIn, 24 October 2026

The fitness check is itself a control. It runs at the point of consumption and stops unsuitable data being used. But fitness is one control among many. Every regulated organisation has a wider set of data quality controls covering completeness, accuracy, freshness, lineage, sensitivity and approval. This chapter asks where those controls should be enforced. As AI agents become routine consumers of data, the answer is changing.

The control lifecycle

In most organisations four of these stages are well established. Controls are defined in catalogues, implemented in pipelines and batch jobs, and reported through dashboards to governance forums. The middle stage, enforcement, is where the most opportunity sits. Not because firms are doing it wrong, but because the architectures that support enforcement were built for a different pattern of consumption.

Why enforcement needs to change

Today's data quality model rests on two strong foundations: scheduled batch checks and operational dashboards. Both do a real job. They were designed when consumption was predictable: a few known applications using data on known schedules. Issues found in the morning batch run could be fixed before the next consumption window.

AI agents change that pattern. Many agents make many decisions through many small consumption events in real time. By the time a nightly batch finds a quality issue, the data may already have been used across many agent interactions and built into downstream outputs. This is not a failure of existing approaches. It is a chance to extend them by adding a real time enforcement layer alongside the batch and dashboard layers already in place.

Agents as control invokers, not control authors

The shift is simple in concept. If every consumer of data calls a runtime control service before consuming, every consumer becomes a control point.

That does not mean every agent has its own controls. That would be chaos. It means every agent calls shared control services that live centrally in the data architecture. Controls live as services, agents call them, outcomes are structured and breaches are routed automatically.

The extended lifecycle

The five stages keep their names but deepen in practice:

  • Defined in a machine readable control catalogue, not only a policy document.
  • Implemented as services that can be called at runtime, alongside existing batch and pipeline checks.
  • Enforced at the point of consumption, by every agent that touches the data.
  • Monitored through structured logs of every invocation and outcome.
  • Reported as real time breach notifications to data owners and aggregated trends for governance.

Each stage builds on what already exists. The runtime layer adds to it. It does not replace it.

Which controls fit this pattern

Completeness, accuracy, freshness, lineage, sensitivity and approval controls all translate naturally into runtime services. Not every control needs to run at runtime, and some work best as periodic checks. The skill is in identifying which controls protect the highest risk consumption decisions and bringing those forward to the moment of use.

What a runtime control looks like

A runtime control is a small, focused service. It accepts a request, evaluates it against a defined rule and returns a structured outcome. Here is a freshness control:

control:
  id: freshness_counterparty
  type: freshness
  scope: counterparty_data

threshold:
  max_staleness_minutes: 60
  reference_field: last_updated_timestamp

invocation:
  contract: synchronous
  blocking: true

response:
  pass: data may be consumed
  warn: data may be consumed with caveat
  fail: consumption blocked, breach event published

breach_handling:
  notify: counterparty_data_owner
  log: control_event_bus
  aggregate: governance_dashboard

Breach handling closes the loop

When a control returns a breach, three things happen automatically. The consumer receives a structured response saying what failed and what to do. The data owner is notified through the established feedback channel. The breach is captured for governance reporting and trend analysis. There is no separate process to remember. The architecture does it, and all five stages of the lifecycle run connected and in real time.

How to build it

  1. Catalogue the controls. Gather the controls already defined in policies and standards. Prioritise those that protect the highest risk consumption decisions.
  2. Implement them as runtime services. For each priority control, build a small service using the same pattern as the fitness service.
  3. Embed them in agent consumption. Update agents and applications to call the relevant control before using data. It is a coordinated change, but a small one in each agent.
  4. Wire the feedback loops. Connect breach outcomes to data owners, governance dashboards and audit trails, so the loop closes itself.
Chapter 5

The operating model

First published on LinkedIn, 31 October 2026

The previous chapters answered three questions. Where should AI get its data? Is the data suitable for the task? Are the rules enforced when the data is used? One question remains: how does this become something an organisation can actually run?

One capability, not five projects

The biggest risk in adopting the network is treating each component as a separate workstream: five teams, five backlogs and five governance forums, all moving at different speeds. The result is five things that do not talk to each other.

The network is one capability. Its components share contracts, vocabularies and identities, and together they produce coherent context, which is the whole point. Treating it as one capability is the difference between a working network and a collection of disconnected catalogues.

Governed access

Fitness and access are different things. Data may be fit for transaction monitoring, but the agent asking for it may not be entitled to that data for that purpose. Access checks are runtime services, like fitness and controls: same pattern, different question.

This is where AI agents need to be treated as participants in their own right. Each agent needs its own identity, its own entitlements and a purpose it declares at runtime. Treating an agent as a generic service account works in a sandbox. It does not survive a regulator asking who consumed what, when, and on whose authority.

The organisational reality map

The final component is the one most often skipped. The network must mirror how the organisation actually works: its domains, its processes, its escalation paths and its existing governance forums.

The trap is the beautifully designed network that nobody recognises. A target architecture drawn in isolation from how the business runs will not be adopted. The teams expected to populate it will quietly resist, and the forums expected to govern it will keep using the spreadsheets they already trust. Adoption comes from grounding the network in current reality. Existing data domains become the unit of ownership. Existing escalation paths carry breach events. Existing forums consume the network's outputs. The network does not replace how the organisation works. It gives that work better foundations.

Five roles

The network in operation

When an agent does its job, every consumption decision flows through the network. The agent declares its identity, its purpose and the data it needs. The source registry returns the approved source. The fitness framework confirms suitability for the declared purpose. Runtime controls check completeness, accuracy, freshness, lineage and sensitivity. Governed access confirms the agent is entitled. The agent consumes, and the full interaction is logged. Any breach notifies the relevant data owner and feeds the governance dashboard.

The agent does not assemble this sequence itself. It is the network's runtime fabric. Each step is a service call that returns a structured answer.

The maturity journey

Most organisations are not starting from zero. Catalogues, dashboards and governance forums already exist. The question is how to evolve them, in what order and at what pace.

This is multi year work for most firms. The good news is that every stage pays for itself. The first time an agent consults the registry instead of guessing, the network has already earned its place.

What good looks like

When the network is running, AI knows four things at any moment: where to get data, whether it is fit, whether the rules are met, and whether the consumer is authorised. With the organisational reality map underneath, it also knows how the business works: who owns what, where breaches escalate and which forums govern. Trust, speed, governance and scale stop competing and start reinforcing each other.

Conclusion

Start somewhere

The Coherent Memory Network is not a product. It is a discipline: part architecture, part governance, part organisational design. It is built component by component, domain by domain, on top of what most regulated firms already have.

The argument of this paper is simple. AI does not lack data. It lacks context. The network is how organisations give it that context, in a form it can navigate, with the controls and accountability a regulator expects. Organisations that invest in this foundation will scale AI sustainably. The path is not short, but every stage delivers value and every component strengthens the next.

Start somewhere. Build one component well. The rest follows.
